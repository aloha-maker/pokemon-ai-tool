## 作業タイトル
P2-3: APIレスポンス形式の統一

### 現状
- APIの成功時レスポンス形式に一貫性がない。データ本体を直接返す場合と、`{"message": ...}` のようなオブジェクトでラップする場合が混在している。
- エラーレスポンスは `{"error": ...}` で概ね統一されているが、一部 `{"success": False, "error": ...}` という形式が使われている箇所がある。
- クライアント側は、エンドポイントごとに異なるレスポンス形式をハンドリングする必要があり、実装が煩雑になっている。

### 修正内容
- APIから返されるすべてのレスポンスを、標準的な構造（エンベロープ）で統一する。
- JSend規約などを参考に、以下のような形式を導入する。
  - 成功時: `{"status": "success", "data": ...}`
  - 失敗時（クライアントエラー）: `{"status": "fail", "data": {"key": "message"}}`
  - 失敗時（サーバーエラー）: `{"status": "error", "message": "Internal Server Error"}`

### 手順
1. レスポンスを標準形式に変換するためのデコレータまたはヘルパー関数を作成する。
2. まず1つのAPIエンドポイント（例: `GET /api/parties`）に新しいレスポンス形式を適用する。
3. フロントエンドのJavaScriptコードを修正し、新しいレスポンス形式に対応させる。
4. 該当APIの結合テストを修正し、新しいレスポンス形式を検証するように変更する。
5. 動作確認後、他のすべてのAPIエンドポイントに新しいレスポンス形式を順次適用していく。
6. すべてのAPIで `{"error": ...}` 形式を廃止し、新しい形式に統一する。

### 影響範囲
- `src/routes/api/` 配下の全ファイル
- `static/js/` 配下のJavaScriptファイル（APIを呼び出している箇所）
- `tests/` 配下のAPI結合テスト

### テスト方法
- 修正したAPI結合テストをすべて実行し、パスすることを確認する。
- ブラウザで実際に画面を操作し、すべての機能が正常に動作することを確認する（E2Eテスト）。

### 工数
大

### リスク
- 影響範囲がフロントエンドを含むアプリケーション全体に及ぶため、修正漏れがあると機能不全に陥る箇所が発生しやすい。
- 一括での変更はリスクが高いため、エンドポイントごとに段階的に進める必要がある。
