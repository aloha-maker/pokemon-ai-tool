### 3.4. 【P1-4】メモリリークの修正

*   **目的:** `src/routes/api/video.py` で利用されているグローバルな `state.video_tasks` ディクショナリが、完了したタスクを保持し続けることによるメモリリークを解消する。
*   **想定工数:** 4時間

#### 3.4.1. 詳細修正手順

1.  **問題の特定:** `state.video_tasks` にタスクが追加されるだけで、削除される処理がないことを確認します。
2.  **修正方針の決定:**
    *   **案A:** タスクのステータスを返すAPIエンドポイント (`/api/video/status/<task_id>`) が呼び出された際に、タスクが `status == 'completed'` または `'failed'` であれば、`state.video_tasks` から該当タスクを削除する。
    *   **案B:** バックグラウンドスレッドを起動し、定期的に `state.video_tasks` をスキャンして完了済みのタスクを削除する。
3.  **実装:**
    *   クライアント側が必ずステータスを確認しに来ることを前提とし、よりシンプルな**案A**を採用します。
    *   ステータス確認エンドポイントのロジックを修正し、完了済みタスクを `pop()` で取り出して返すように変更します。

#### 3.4.2. コード例 (`src/routes/api/video.py` 内を想定)

**修正前**
```python
from src import state

@api.route('/video/status/<task_id>')
def get_video_status(task_id):
    task = state.video_tasks.get(task_id)
    if not task:
        return jsonify({"error": "Task not found"}), 404
    return jsonify({"status": task['status'], "progress": task['progress']})
```

**修正後**
```python
from src import state
from threading import Lock

# 同時アクセスによる競合を避けるためのロック
tasks_lock = Lock()

@api.route('/video/status/<task_id>')
def get_video_status(task_id):
    with tasks_lock:
        task = state.video_tasks.get(task_id)
        if not task:
            return jsonify({"error": "Task not found"}), 404

        response = {"status": task['status'], "progress": task['progress']}

        # タスクが完了または失敗していたら、辞書から削除する
        if task['status'] in ['completed', 'failed']:
            state.video_tasks.pop(task_id, None) # popで安全に削除

    return jsonify(response)
```

#### 3.4.3. 影響範囲

*   `src/routes/api/video.py`
*   `src/state.py`
*   動画解析機能のステータス取得部分。

#### 3.4.4. テスト方法

*   動画解析タスクを開始するAPIを呼び出します。
*   タスクが完了するまでステータス取得APIをポーリングします。
*   タスク完了後、再度ステータス取得APIを呼び出し、タスクが見つからない (`404 Not Found`) ことを確認します。
*   サーバーのメモリ使用量を監視し、タスク完了後にメモリが解放されることを確認します。

#### 3.4.5. リスクと対策

*   **リスク:** ステータス取得APIが完了前に複数回呼び出される、あるいはクライアントが結果を取得しに来ない場合、タスクが削除されない可能性があります。
*   **対策:** より堅牢な対策として、タイムアウト機構を持つバックグラウンドスレッド（案B）の導入を将来的に検討します。今回はまずシンプルな修正でメモリの無限増加を防ぐことを優先します。
