## 作業タイトル
P2-1: サービスレイヤーの導入

### 現状
- ビジネスロジックがAPIルート(コントローラ層)やデータアクセス層(`DatabaseManager`)に散在している。
- `routes/api/dashboard.py` の `get_dashboard_data` など、APIエンドポイント関数内で複雑なデータ加工や複数回のDBアクセスが行われている（ファットコントローラー問題）。
- コードの再利用性が低く、ビジネスロジックの単体テストが困難。

### 修正内容
- APIルートとデータアクセス層の間にサービスレイヤーを導入し、散在しているビジネスロジックをサービス層に集約する。
- APIルートはリクエストの検証とサービス層の呼び出しに専念させ、責務を明確化する。

### 手順
1. `src/services` ディレクトリを作成する。
2. ビジネスロジックの単位でサービスクラスを作成する (例: `src/services/dashboard_service.py`, `src/services/party_service.py`)。
3. `routes/api/dashboard.py` の `get_dashboard_data` 関数内にあるデータ集計・加工ロジックを `DashboardService` クラスのメソッドとして移管する。
4. `routes/api/dashboard.py` をリファクタリングし、`DashboardService` を呼び出すだけのシンプルな実装に変更する。
5. 他のAPIエンドポイント（パーティ管理、AI予測など）についても同様に、ビジネスロジックを適切なサービスクラスに移管する。
6. 新しく作成したサービスクラスに対応する単体テストを作成する。

### 影響範囲
- `src/` (新規ディレクトリ `services/` を作成)
- `src/routes/api/` 配下の全ファイル
- `tests/` (新規テストファイルを追加)

### テスト方法
- `pytest` を用いて、新設したサービスクラスの各メソッドに対する単体テストを実行する。
- Flaskのテストクライアントを使用し、リファクタリングされたAPIエンドポイントの結合テストを実行する。リファクタリング前後でAPIのレスポンス仕様が変わらないことを確認する。

### 工数
中

### リスク
- 影響範囲が広いため、関連するAPIの挙動が変わってしまうデグレードのリスクがある。
- **前提条件:** このタスクに着手する前に、【P1】で定義されたテスト基盤が構築され、主要なAPIエンドポイントに対するテストが存在することが強く推奨される。
