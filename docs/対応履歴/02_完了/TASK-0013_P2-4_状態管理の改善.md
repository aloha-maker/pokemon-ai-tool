# 【対応履歴フォーマット】
## 作業タイトル
P2-4: グローバル変数による状態管理の改善

### 現状
- `src/state.py` に定義されたグローバル変数（`video_tasks`, `ocr_thread`, `shared_game_state` など）を用いて、スレッド間の状態共有が行われている。
- このアプローチは、複数のスレッドが同時に同じ変数を書き換えることによる競合状態（Race Condition）のリスクを抱えている。
- グローバル変数はアプリケーションのどこからでも変更可能なため、問題発生時の原因特定が非常に困難である。
- グローバルな状態に依存するコンポーネントは、独立した単体テストを書くことがほぼ不可能であり、品質保証を難しくしている。

### 修正内容
- `src/state.py` を完全に廃止し、グローバル変数に依存しない、堅牢でテスト可能な状態管理機構を導入する。
- アプリケーション全体の実行時状態をカプセル化する専用のクラス `src/core/app_state.py:AppState` を新たに設計・導入する。
- Flaskのアプリケーションファクトリ (`app.py`) で `AppState` クラスをインスタンス化し、Flaskアプリケーションのライフサイクルと状態を紐付ける。
- これまでグローバル変数を直接参照していたすべてのモジュール（APIエンドポイント、SocketIOハンドラ、バックグラウンドワーカー）が、Flaskのアプリケーションコンテキスト (`current_app.state`) を通じて、安全に状態へアクセスするようにリファクタリングする。

### 手順
1.  **`AppState` クラスの新規作成**
    -   `src/core/app_state.py` という新しいファイルを作成します。
    -   `src/state.py` に定義されているすべてのグローバル変数と、それに関連するロック (`game_state_lock`) を、`AppState` クラスのインスタンス変数として移動させます。

    ```python
    # src/core/app_state.py
    import threading

    class AppState:
        def __init__(self):
            self.video_tasks = {}
            self.capture_thread = None
            self.ocr_thread = None
            self.background_thread_stop_event = threading.Event()
            self.shared_game_state = {}
            self.game_state_lock = threading.Lock()
            # 他のグローバル変数も同様に移動
    ```

2.  **アプリケーションファクトリ (`app.py`) の修正**
    -   `create_app` 関数の内部で、作成した `AppState` をインスタンス化します。
    -   Flaskの `app` オブジェクトに、`state` という属性名でインスタンスをアタッチします。これにより、リクエストコンテキスト内から `current_app.state` としてアクセスできるようになります。

    ```python
    # app.py の修正箇所
    from src.core.app_state import AppState # 新しくインポート

    def create_app():
        app = Flask(__name__, instance_relative_config=True)
        
        # ... (既存の設定) ...

        # AppStateをインスタンス化してappにアタッチ
        app.state = AppState()

        # ... (Blueprintの登録など) ...
        
        return app, socketio
    ```

3.  **`sockets/handlers.py` のリファクタリング**
    -   `from src.state import ...` というインポート文をすべて削除します。
    -   `shared_game_state` や `game_state_lock` などの状態変数にアクセスしている箇所を、`current_app` をインポートして `current_app.state.shared_game_state` のように修正します。

    ```python
    # src/sockets/handlers.py の修正例
    from flask import current_app
    # from src.state import shared_game_state, game_state_lock # 削除

    @socketio.on('start_analysis')
    def handle_start_analysis(data):
        # ...
        with current_app.state.game_state_lock:
            current_app.state.shared_game_state.clear()
        # ...
    ```

5.  **`workers` ディレクトリ配下のモジュールのリファクタリング**
    -   バックグラウンドワーカーはリクエストコンテキスト外で動作するため、`current_app` を直接使えません。
    -   ワーカーを起動する際 (`socketio.start_background_task` など) に、引数として `app.state` を渡すように修正します。

### テスト方法
- **単体テスト**:
    - `src/core/app_state.py` に対する単体テストを新規に作成し、状態の初期化や更新が正しく行われることを確認します。
- **結合テスト**:
    - リアルタイム解析機能（「解析開始」ボタン）が、リファクタリング前と同様に動作し、画面にOCR結果が反映されることを手動で確認します。
    - 動画アップロード機能が正常に動作し、タスクのステータスが正しく更新・取得できることを手動で確認します。
- **検証項目**:
    - アプリケーション起動後、各機能がエラーなく動作するか。
    - リアルタイム解析中に、複数のクライアントが接続しても状態が混線しないか（可能であれば）。
    - 長時間起動後も、メモリリークが発生していないことを確認します（`video_tasks`が適切にクリーンアップされるかなど）。

### 工数
大

### リスク
- アプリケーションの実行時状態を管理する中核部分の変更であり、リファクタリングに誤りがあると、リアルタイム処理が停止する、状態が更新されないなどの致命的な不具合に繋がる可能性があります。
- バックグラウンドワーカーへの状態の引き渡しは特に注意が必要で、実装を誤るとワーカーが古い状態を参照し続ける、あるいはクラッシュする危険性があります。
- 自動テストがない中での広範囲なリファクタリングとなるため、手動テストで見逃されるエッジケースが存在する可能性があります。
