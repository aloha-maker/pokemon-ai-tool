ポケモン対戦で自分と相手のパーティをログとしてテーブルに保存したいです。

ポケモン名以外に相手のニックネーム、技構成、テラスタル、持ち物、勝敗の結果、相手の順位、バトルID（自動採番されるキー）、お互いの選出されたポケモン、先発のポケモン、登録日時などの情報を入れ込みたいです。

他に登録した方が良い項目は補完してください。



上記踏まえたテーブル定義を作成してください。

SQLiteです。

より詳細な分析や将来的な拡張を見据えた、本格的な複数テーブル構成のデータベースを設計します。

これは「**データベースの正規化**」という考え方に基づいています。データを役割ごとにテーブルへ分割することで、情報の重複をなくし、データの一貫性を保ちやすくする設計手法です。

-----

### 全体像：テーブルの関係

４つのテーブルが互いに連携し合う構成です。

1.  `battles_log` **(対戦テーブル)**: 対戦１回ごとの基本情報を記録します。これが全ての情報の起点となります。
2.  `parties_log` **(パーティ選出テーブル)**: どの対戦(`battle_id`)で、どちらのプレイヤーが、どのポケモン(`pokemon_id`)をパーティに入れ、実際選出したかを記録します。
3.  `pokemons_log` **(ポケモン個別データテーブル)**: 相手のパーティで登場したポケモンの詳細データ（技、持ち物など）を記録します。同じポケモンが何度も登場する場合も、ここに１つだけ登録し、IDで管理します。
4.  `raw_battle_events_log` **(生ログテーブル)**: 前回設計した、時系列のイベントログです。`battles`テーブルと紐付けます。

-----

### 各テーブルのCREATE TABLE文

#### 1\. battles (対戦テーブル)

まず、対戦の全体像を記録するテーブルです。シンプル版のテーブルから、ポケモンに関する情報を抜き出した形になります。

```sql
CREATE TABLE battles (
    battle_id INTEGER PRIMARY KEY AUTOINCREMENT,
    battle_date TEXT NOT NULL DEFAULT (DATETIME('now', 'localtime')),
    season INTEGER,
    regulation TEXT,
    battle_format TEXT NOT NULL CHECK(battle_format IN ('シングル', 'ダブル')),
    my_rank INTEGER,
    opponent_rank INTEGER,
    result TEXT NOT NULL CHECK(result IN ('勝ち', '負け')),
    my_first_pokemon TEXT,
    opponent_first_pokemon TEXT,
    memo TEXT
);
```

-----

#### 2\. pokemons (ポケモン個別データテーブル)

次に、対戦で見かけた相手のポケモンの詳細データを格納するテーブルです。

**ポイント**:

  * ニックネーム、技構成、テラスタル、持ち物が全く同じポケモンは、このテーブルに１度しか登録しません。
  * これにより、「この技構成のカイリューに何回遭遇したか」といった集計が容易になります。

<!-- end list -->

```sql
CREATE TABLE pokemons (
    pokemon_id INTEGER PRIMARY KEY AUTOINCREMENT,
    pokemon_name TEXT NOT NULL,
    nickname TEXT,
    moves TEXT,
    terastal_type TEXT,
    item TEXT,
    ability TEXT
);
```

  * `moves`: `["しんそく", "じしん", "アンコール", "りゅうのまい"]` のようにJSON形式のテキストで技を４つ保存します。
  * `ability`: 特性を追加しました。後の分析で役立ちます。

-----

#### 3\. parties (パーティ選出テーブル)

このテーブルが、**対戦**と**ポケモン**を結びつける「中間テーブル」の役割を果たします。

**ポイント**:

  * `battle_id` と `pokemon_id` の組み合わせで、「どの対戦」で「どのポケモン」が使われたかを表現します。
  * `is_opponent` で自分か相手か、`is_selected` で選出されたかどうかを区別します。

<!-- end list -->

```sql
CREATE TABLE parties (
    party_id INTEGER PRIMARY KEY AUTOINCREMENT,
    battle_id INTEGER NOT NULL,
    pokemon_id INTEGER,
    pokemon_name TEXT NOT NULL,
    is_opponent BOOLEAN NOT NULL,
    is_selected BOOLEAN NOT NULL,
    FOREIGN KEY (battle_id) REFERENCES battles (battle_id),
    FOREIGN KEY (pokemon_id) REFERENCES pokemons (pokemon_id)
);
```

  * **自分のポケモン**: 自分のポケモンはマスターデータ（技構成などが固定）とみなし、`pokemon_id` は `NULL` にして `pokemon_name` だけを記録します。
  * **相手のポケモン**: 相手のポケモンは `pokemons` テーブルに詳細を登録し、その `pokemon_id` をここに記録します。

-----

#### 4\. raw\_battle\_events (生ログテーブル)

最後に、前回設計した生ログテーブルです。これは`battles`テーブルとだけ連携します。

```sql
CREATE TABLE raw_battle_events (
    event_id INTEGER PRIMARY KEY AUTOINCREMENT,
    battle_id INTEGER NOT NULL,
    log_timestamp TEXT NOT NULL DEFAULT (strftime('%Y-%m-%d %H:%M:%f', 'now', 'localtime')),
    sequence INTEGER NOT NULL,
    game_text TEXT,
    my_pokemon_1_name TEXT,
    my_pokemon_1_hp_percent REAL,
    my_pokemon_1_status TEXT,
    my_pokemon_2_name TEXT,
    my_pokemon_2_hp_percent REAL,
    my_pokemon_2_status TEXT,
    opponent_pokemon_1_name TEXT,
    opponent_pokemon_1_hp_percent REAL,
    opponent_pokemon_1_status TEXT,
    opponent_pokemon_2_name TEXT,
    opponent_pokemon_2_hp_percent REAL,
    opponent_pokemon_2_status TEXT,
    triggered_ability TEXT,
    field_effects TEXT,
    FOREIGN KEY (battle_id) REFERENCES battles (battle_id)
);
```

-----

### この設計のメリット

  * **データ効率が良い**: 同じ技構成のサーフゴーに100回会っても、`pokemons`テーブルへの登録は1回で済みます。
  * **分析しやすい**: 「"こだわりスカーフ"を持ったサーフゴーとの対戦成績」や「"ゴールドラッシュ"の採用率」といった、詳細な条件でのデータ集計がSQLで簡単に行えます。
  * **拡張性が高い**: 将来的に「努力値」や「性格」といった項目を追加したくなっても、`pokemons`テーブルを修正するだけで対応できます。

運用は少し複雑になりますが、データを資産として活用していく上では非常に強力な構成です。

対戦中のログを記録するテーブルも設計してください。

記録情報は画面上のテキスト、ポケモン名、HP、状態異常、特性の発動です。
記録は1秒間に1回を切り取って保存するため、ターンなどの判断は出来ません。

このログテーブルは生データとして利用し、加工してターンを判断したりするために使います。

今後としては、この情報を元にターンごとに何が起きたか、場の状態はどうなっているかを判別できるようにし、機械学習のためのデータとして扱えるようにする予定です。

承知いたしました。対戦中の出来事を時系列で記録するための「生ログ」テーブルですね。

機械学習での利用を視野に入れ、1秒ごとのスナップショットから後で文脈を再構築できるよう、場の状態をできるだけ詳細に記録できるテーブルを設計しました。

これは、前回作成した`battle_logs`テーブルの\*\*1回の対戦（battle\_id）\*\*に対して、\*\*多数のログ（raw\_battle\_events）\*\*が紐づく関係になります。

### 生ログ記録用テーブルの設計

このテーブルは、シングル・ダブルバトル両方に対応できるよう、場に出ているポケモンをそれぞれスロット1、スロット2として記録できるようにしています。

#### CREATE TABLE文

```sql
CREATE TABLE raw_battle_events_log (
    event_id INTEGER PRIMARY KEY AUTOINCREMENT,
    battle_id INTEGER NOT NULL,
    log_timestamp TEXT NOT NULL DEFAULT (strftime('%Y-%m-%d %H:%M:%f', 'now', 'localtime')),
    sequence INTEGER NOT NULL,
    game_text TEXT,
    my_pokemon_1_name TEXT,
    my_pokemon_1_hp_percent REAL,
    my_pokemon_1_status TEXT,
    my_pokemon_2_name TEXT,
    my_pokemon_2_hp_percent REAL,
    my_pokemon_2_status TEXT,
    opponent_pokemon_1_name TEXT,
    opponent_pokemon_1_hp_percent REAL,
    opponent_pokemon_1_status TEXT,
    opponent_pokemon_2_name TEXT,
    opponent_pokemon_2_hp_percent REAL,
    opponent_pokemon_2_status TEXT,
    triggered_ability TEXT,
    field_effects TEXT,
    FOREIGN KEY (battle_id) REFERENCES battle_logs (battle_id)
);
```

-----

### 各項目の詳細

| カラム名 | データ型 | 説明 |
| :--- | :--- | :--- |
| `event_id` | INTEGER | **イベントID**: ログ1行ごとを識別する番号です。自動で採番されます (主キー)。 |
| `battle_id` | INTEGER | **バトルID**: どの対戦のログかを示すIDです。`battle_logs`テーブルと紐付けます (外部キー)。 |
| `log_timestamp` | TEXT | **記録タイムスタンプ**: このログが記録された日時です。ミリ秒まで自動記録されます。 |
| `sequence` | INTEGER | **シーケンス番号**: 対戦開始からの通し番号 (例: 0, 1, 2...秒)。ログの順序を保証します。 |
| `game_text` | TEXT | **画面テキスト**: 「カイリュー の しんそく！」のような、ゲーム画面に表示されるテキストをそのまま記録します。 |
| `my_pokemon_1_name` | TEXT | **自分側ポケモン1の名前**: 自分側の場、スロット1にいるポケモンの名前。 |
| `my_pokemon_1_hp_percent` | REAL | **自分側ポケモン1のHP率**: HPゲージの割合を `1.0` (満タン) ～ `0.0` (ひんし) の数値で記録します。 |
| `my_pokemon_1_status` | TEXT | **自分側ポケモン1の状態異常**: 「どく」「まひ」「ねむり」などを記録します。なければ`NULL`。 |
| `my_pokemon_2_...` | - | **自分側ポケモン2**: ダブルバトル用。シングルバトルでは`NULL`になります。 |
| `opponent_pokemon_1_...` | - | **相手側ポケモン1**: 相手側の場、スロット1のポケモン情報。 |
| `opponent_pokemon_2_...` | - | **相手側ポケモン2**: ダブルバトル用。シングルバトルでは`NULL`になります。 |
| `triggered_ability` | TEXT | **発動した特性**: 「いかく」「ひでり」など、その瞬間に発動した特性の名前を記録します。 |
| `field_effects` | TEXT | **場の効果**: 天候、フィールド、おいかぜ、トリックルームなどの場の状態をJSON形式で記録します。(下記参照) |

#### 🤖 なぜHPをパーセントで記録するのか？

最大HPが不明な相手ポケモンのHPも同じ基準で扱えるため、後のデータ分析や機械学習で非常に扱いやすくなります。

#### `field_effects` のJSONデータ例

場の状態は複数同時に発生しうるため、JSON形式で記録すると柔軟に対応できます。

```json
{
  "weather": "あめ",
  "field": "エレキフィールド",
  "my_side": ["おいかぜ", "リフレクター"],
  "opponent_side": ["ステルスロック"]
}
```

このテーブル設計により、対戦中のあらゆる瞬間をデータとして蓄積し、後から「どのテキストが表示された時に、誰のHPがどれだけ変動したか」といった詳細な分析を行うための強力な土台となります。
