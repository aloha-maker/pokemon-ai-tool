`tests`ディレクトリの調査結果

  1. 存在するテストファイルとその内容

   * 該当なし: testsディレクトリ、およびそのサブディレクトリには、Pythonのソースコードファイル (.py) は一切存在しませんでした。
   * ディレクトリ内に存在する可能性のあるファイルは、テスト用の画像データや設定ファイルのみと推測されます。

  2. テストフレームワークの使用状況

   * 未使用: テストコードが存在しないため、pytestやPython標準のunittestといったテストフレームワークは一切使用されていません。
   * プロジェクトの依存関係（requirements.txtなど）にテストフレームワークが含まれている可能性はありますが、少なくとも現状では活用されていません。

  3. テストカバレッジの推定

   * 0%: 自動化されたテストコードが存在しないため、コードカバレッジは0%です。
   * アプリケーションのどの機能も、自動化されたテストによって品質が保証されていない状態です。開発者が手動で動作確認を行っているものと推測されます。

  4. テストが書かれていない重要機能のリスト

  カバレッジが0%であるため、アプリケーションのすべての機能にテストが書かれていません。その中でも、品質保証や将来の改修時の安全性（デグレード防止）の観点から、特にテストを書くべき重要な機能は以下の通りです。

   * データベースアクセス層 (`src/database/manager.py`)
       * 理由: アプリケーションのデータ永続化を担う最も重要なコンポーネントです。CRUD操作や複雑なJOIN、集計クエリが正しく動作することは、全機能の前提となります。
       * テストすべきこと: 各メソッド（add_party, get_win_rate_by_opponentなど）が、期待通りのSQLを発行し、正しいデータを返す/書き込むこと。

   * AIロジック (`src/ai/*.py`)
       * 理由: 勝率予測やパーティ生成といった、このアプリケーションのコアとなる知的機能です。ロジックが複雑であるため、手動での検証には限界があります。
       * テストすべきこと: WinRatePredictorが特定の対面で正しい有利不利を判定するか。PartyGeneratorがコンセプトに沿ったポケモンを選出するか、など。

   * APIエンドポイント (`src/routes/api/*.py`)
       * 理由: アプリケーションの外部インターフェースであり、クライアントとの契約（リクエスト形式、レスポンス形式、ステータスコード）を守っていることを保証する必要があります。
       * テストすべきこと:
         各エンドポイントが、正常なリクエストに対して2xx系のステータスコードと期待通りのレスポンスを返すこと。不正なリクエスト（バリデーションエラー）に対して4xx系のステータスコードとエラーメッセージを返すこと。

   * コアビジネスロジック (`src/core//*.py`)**
       * 理由: OCR処理、ダメージ計算、画面キャプチャなど、専門的で複雑な処理が含まれます。
       * テストすべきこと: calculator.pyのダメージ計算式が正しいか。ocr_processor.pyが画像から期待通りにテキストを抽出・補正できるか、など。

  総括

  現状、このプロジェクトは自動化されたテストが全く存在しない状態であり、これは品質保証と将来のメンテナンス性において極めて重大なリスクです。

  機能追加やリファクタリングを行うたびに、既存の機能が意図せず壊れてしまう「デグレード」が発生する可能性が非常に高く、その確認はすべて手動で行う必要があります。

  今後の開発を進めるにあたり、何よりも優先してテストフレームワーク (`pytest`を推奨) を導入し、まずは `DatabaseManager` などの基盤となる部分から単体テストを整備していくことを強く推奨します。

テスト不在状況下でのリファクタリング・リスク評価

  自動テストによる「安全網」がない状態でのリファクタリングは、たとえ小さな変更であっても、アプリケーション全体に予期せぬ不具合（デグレード）を引き起こす可能性があり、極めて危険です。以下に、機能ごとの具体的な
  リスクを評価します。

  1. DatabaseManager.save_battle_result_with_log

   * リスクレベル: 極めて高い

  この関数は、複数のテーブル (battles, parties_log, pokemons_log, raw_battle_events) にまたがる複雑な書き込み処理を行う、アプリケーションの心臓部の一つです。

   * 想定されるリスク:
       * データ破損・不整合: リファクタリングの過程でロジックに誤りが生じると、中間テーブルのIDがずれる、自分と相手のフラグ (is_opponent) が逆になる、選出情報 (is_selected)
         が欠落するなど、データの整合性が完全に破壊される可能性があります。一度不整合なデータが書き込まれると、後から修正するのは非常に困難です。
       * トランザクションの崩壊: 現在は try...except...rollback
         で保護されていますが、処理を複数のメソッドに分割する際にトランザクションの管理を誤ると、処理の途中でエラーが発生した際にデータベースが中途半端な状態で放置される（例:
         battlesレコードは作られたが、parties_logが空のまま）危険性があります。
       * 冪等性（べきとうせい）の喪失: 現在は「既存ログを削除してから挿入」することで、同じリクエストを複数回送っても結果が同じになる冪等性を担保しています。このロジックを誤ると、リクエストの再送などで重複したロ
         グデータが大量に生成される可能性があります。
       * サイレントなバグ: 最も恐ろしいのは、エラーを発生させずに間違ったデータを静かに書き込み続けるバグです。例えば、相手のテラスタイプを常に自分のものとして記録してしまう、といったバグは、後から分析ダッシュボ
         ードの数値がおかしいことに気づくまで発見が遅れます。

  2. DatabaseManager._get_party_members

   * リスクレベル: 高い

  この関数は、典型的なN+1クエリの発生源であり、パフォーマンス改善のためのリファクタリング対象となりやすい箇所です。しかし、複数のテーブルをJOINする複雑な読み取り処理であり、リスクを伴います。

   * 想定されるリスク:
       * データ構造の変化によるAPI破壊: このメソッドは get_party_by_id など複数の公開APIから呼び出されています。リファクタリングによって返却されるデータ構造（JSONのキーの名前や階層）がわずかでも変わると、APIのレ
         スポンス形式が変わり、フロントエンド（クライアント）が正常に動作しなくなります。
       * 不正確なデータ取得: 複雑な JOIN クエリへの変更は、バグを生みやすい代表的な例です。例えば、LEFT JOIN と INNER JOIN
         の選択を誤ると、メンバーが欠落したり、逆にデータが重複して返されたりする可能性があります。
       * パフォーマンスの悪化: N+1問題を解決しようとして書いた JOIN クエリが非効率（インデックスが効いていないなど）だった場合、逆にパフォーマンスが悪化する可能性もゼロではありません。

  3. party_generator.generate

   * リスクレベル: 高い

  AIによるパーティ生成ロジックは、多数のルールと、randomによるランダム性を含む複雑なアルゴリズムの塊です。

   * 想定されるリスク:
       * 戦略的価値のサイレントな低下: リファクタリング後も、形式上は「6体のパーティ」が生成されるため、一見すると成功しているように見えます。しかし、内部のスコアリングや選出ロジックのバグにより、生成されるパー
         ティのタイプバランスやコンセプトとの整合性が著しく低下している可能性があります。これは手動テストでは非常に検出しにくい「品質のデグレード」です。
       * 再現性のないバグ: random
         を使用しているため、特定の条件下でしか発生しないバグの特定と修正が困難になります。テストコードであれば、乱数のシード値を固定して、常に同じ結果を再現させながら安全にリファクタリングを進められます。
       * 無限ループやクラッシュ: 候補選出のロジックを誤ると、特定の入力（利用可能なポケモンの組み合わせ）に対して無限ループに陥ったり、ゼロ除算でクラッシュしたりするリスクがあります。

  4. win_rate_predictor関連

   * リスクレベル: 高い

  パーティ生成と同様、アプリケーションの「賢さ」を担うコア機能であり、そのロジックの正確性がすべてです。

   * 想定されるリスク:
       * 予測結果の反転: タイプ相性のスコア計算 (_calculate_matchup_score) の符号 (+と-) を一つ間違えるだけで、有利な選出を「不利」、不利な選出を「有利」と完全に逆の判定をしてしまう可能性があります。
       * エッジケースの考慮漏れ: 「ゴーストタイプへのノーマル技（効果なし）」や「複合タイプへの4倍弱点/4分の1耐性」など、特殊な相性計算のロジックがリファクタリングによって壊れる可能性があります。
       * APIコントラクト違反: このロジックは /api/ai/predict エンドポイントから呼び出されます。返却する辞書のキー (recommended_teamなど) を変更してしまうと、APIの仕様が変わり、クライアントを破壊します。

  5. APIエンドポイント全般

   * リスクレベル: 高い

  各エンドポイントは、アプリケーションと外部クライアント（フロントエンド）をつなぐ「契約(コントラクト)」です。内部ロジックの変更が、この契約を破壊するリスクを常に伴います。

   * 想定されるリスク:
       * レスポンス形式の破壊: 最も頻繁に発生しうるリスクです。JSONのキー名を変更する、階層構造を変える、配列をオブジェクトに変えるなど、わずかな変更がクライアント側のエラーに直結します。
       * バリデーションロジックの破壊:
         リファクタリングの過程で、リクエストデータのバリデーションロジックが意図せず緩くなったり（不正なデータを受け入れてしまう）、厳しくなったり（正当なリクエストを弾いてしまう）する可能性があります。
       * HTTPステータスコードの変更: 正常系・異常系の処理の流れが変わることで、本来 404 Not Found を返すべきところが 500 Internal Server Error
         になるなど、クライアントが期待する挙動と異なってしまう可能性があります。

  結論

  テストが存在しない状態での上記機能のリファクタリングは、いずれも「高い」または「極めて高い」リスクを伴います。 特に、データ永続化に関わる save_battle_result_with_log
  の変更は、取り返しのつかないデータ破損につながる恐れがあり、絶対に避けるべきです。

  リファクタリングに着手する前に、まずはテストコードを記述し、現状の正しい挙動を保証する「安全網」を構築することが絶対不可欠です。
  テストという保険なしにこれらの複雑な機能に手を入れることは、技術的負債をさらに増大させ、将来のプロジェクトを失敗に導く可能性が非常に高いと言えます。
