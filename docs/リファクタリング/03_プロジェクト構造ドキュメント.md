  プロジェクト構造ドキュメント

  1. 概要

  このドキュメントは「ポケモン対戦補助AIツール」の全体的なアーキテクチャ、主要なコンポーネントの役割、そしてそれらの間の依存関係を記述したものです。プロジェクトに参加する開発者が迅速に全体像を把握することを目
  的とします。

  2. ディレクトリ構造

  プロジェクトは機能ごとに明確に分離されたディレクトリ構造を持っています。


  ┌─────────────────────┬───────────────────────────────────────────────────────────────────────────────────────────────────────────────────┐
  │ ディレクトリ        │ 説明                                                                                                              │
  ├─────────────────────┼───────────────────────────────────────────────────────────────────────────────────────────────────────────────────┤

  3. 主要モジュールと役割

  アプリケーションは以下の主要モジュールによって構成されています。


  ┌───────────────────────────────┬───────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────┐
  │ モジュール                    │ 役割                                                                                                                                                          │
  ├───────────────────────────────┼───────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────┤
  │ app.py                        │ アプリケーションファクトリ。Flaskインスタンスを生成し、src/routes/以下の各Blueprintを登録することで、URLと処理の紐付けを行う。                                │
  │ src/routes/views.py           │ UIルーティング。@app.route()デコレータを使い、'/' や '/database' といったURLに対してHTMLテンプレートを返す。                                                  │
  │ src/routes/api/*.py           │ APIエンドポイント。機能ごとに分割されたRESTful APIを提供する。例：party.pyはパーティのCRUD、ai.pyはAIの予測機能を提供する。                                   │
  │ src/database/manager.py       │ データベース管理。with DatabaseManager() as db:構文で利用できる。SQLクエリを抽象化し、データの取得・保存・更新・削除を行うメソッドを提供する。                │
  │ src/core/capture.py           │ 画面キャプチャ。pygetwindowとPillowを利用して、指定されたウィンドウの映像をキャプチャする。                                                                   │
  │ src/core/ocr/ocr_processor.py │ OCR処理エンジン。キャプチャされた画像フレームを受け取り、設定されたROI（関心領域）に基づいてポケモン名やHPなどの情報をTesseract OCRで読み取る。               │
  │ src/ai/win_rate_predictor.py    │ 勝率予測AI。与えられたパーティ情報に基づき、相手との相性を評価し、最適な選出と予想勝率を計算する。                                                            │
  │ src/ai/party_generator.py     │ パーティ生成AI。指定されたコンセプト（例：「雨パ」「トリックルーム」）に基づき、データベース内のポケモンから最適なパーティを構築する。                        │
  │ src/sockets/handlers.py       │ WebSocketハンドラ。'connect'、'disconnect'、'start_analysis'といったイベントを待ち受け、リアルタイムなOCR処理の開始・停止や結果のクライアントへの送信を行う。 │
  │ src/streaming/generators.py   │ 映像生成・配信。video_stream_generator関数が、キャプチャしたフレームをmultipart/x-mixed-replace形式のレスポンスに変換し、継続的にクライアントへ送信する。       │
  └───────────────────────────────┴───────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────┘

  4. 依存関係とデータフロー

  このシステムの主要な機能は、以下の流れで連携して動作します。

  フロー例1：リアルタイム対戦分析

   1. [フロントエンド] ユーザーがブラウザでトップページを開く。
       * views.py (/) -> index.html が表示される。
   2. [フロントエンド] ユーザーが「解析開始」ボタンをクリック。
       * JavaScriptがWebSocket接続を確立し、start_analysis イベントをサーバーに送信。
   3. [バックエンド] sockets/handlers.py がイベントを受信。
       * 定期的に処理を実行するバックグラウンドタスクを開始。
   4. [バックエンド] バックグラウンドタスク内：
       * streaming/generators.py を通じて core/capture.py がゲーム画面をキャプチャ。
       * core/ocr/ocr_processor.py がキャプチャ画像から盤面情報（ポケモン名、HPなど）を抽出。
       * ai/win_rate_predictor.py が盤面情報をもとに、次に行うべき行動や有利不利を予測。
   5. [バックエンド -> フロントエンド] sockets/handlers.py が、OCR結果とAIの予測を update_data イベントとしてクライアントに送信。
   6. [フロントエンド] JavaScriptがイベントを受信し、画面上の表示をリアルタイムに更新する。

  フロー例2：パーティ登録

   1. [フロントエンド] ユーザーがパーティ管理画面で新しいパーティ情報を入力し、「保存」ボタンをクリック。
   2. [フロントエンド] JavaScriptが fetch APIを使い、POST /api/parties へリクエストを送信。
   3. [バックエンド] routes/api/party.py の add_party() 関数がリクエストを処理。
   4. [バックエンド] database/manager.py の add_party() メソッドを呼び出し、受け取ったデータをデータベースに書き込む。
   5. [バックエンド -> フロントエンド] 処理結果（成功メッセージまたはエラー）をJSON形式でクライアントに返す。

  このように、フロントエンド (templates/static)、API層 (routes)、ビジネスロジック層 (core/ai)、データアクセス層 (database) が明確に分離されており、保守性と拡張性の高いアーキテクチャとなっています。
