設計・アーキテクチャに関する問題点の分析

  srcディレクトリ以下のソースコードを分析した結果、いくつかの設計上の課題が特定されました。これらはアプリケーションの保守性、拡張性、堅牢性に影響を与える可能性があります。

  1. 責任が不明確なモジュール（複数の役割を持つ）

  一部のモジュールが、単一責任の原則から逸脱し、複数の役割を担ってしまっています。

   * `src/database/manager.py` (DatabaseManager クラス)
       * 問題点: このクラスは、データベースの接続管理や単純なCRUD操作（データアクセス層）に留まらず、複雑なビジネスロジックやデータ集計処理（サービス層/ビジネスロジック層）まで担当しています。
       * 具体例:
           * get_win_rate_by_opponent(): SQLで完結させず、複数のクエリ結果をPythonでループ処理して勝率を計算している。
           * get_selection_pattern_win_rate(): 3体の選出パターンごとの勝率という、高度な分析ロジックを内包している。
           * save_battle_result_with_log(): 対戦結果の保存という責務を超え、パーティ情報の処理、マスターデータとの連携、先発ポケモンの記録など、多数の責務を抱えています。
       * 影響: DatabaseManagerが肥大化し、「神クラス（God Class）」になりつつあります。ビジネスロジックの変更がデータアクセス層にまで影響を及ぼし、テストが困難になり、コードの見通しが悪化します。

   * `src/core/ocr_.py`
       * 問題点: このファイルには、OCRでテキストを抽出する GameStateParser と、テンプレートマッチングで画像を認識する PokemonRecognizer という、2つの異なる責務を持つクラスが同居しています。
       * 影響: ファイル名から内容が推測しづらく、関連性の低いコードが同じ場所に存在することで可読性が低下します。
       * 提案: ocr_parser.py と pokemon_recognizer.py のように、クラスごとにファイルを分割すべきです。

  2. 密結合の箇所（変更の影響が広範囲に及ぶ）

  モジュール間の依存性が強く、一つの変更が他の多くのモジュールに修正を強いる箇所が見られます。

   * ルーティング層とデータアクセス層の密結合
       * 問題点: src/routes/api/ 以下のほぼ全てのAPIエンドポイント（ルーティング層）が、DatabaseManager（データアクセス層）を直接呼び出しています。
       * 具体例: src/routes/api/dashboard.py の get_dashboard_data 関数は、db.get_dashboard_summary(), db.get_opponent_pokemon_ranking() など複数の DatabaseManager
         のメソッドを呼び出し、さらにその結果を加工（ソートやフィルタリング）しています。
       * 影響: DatabaseManager のメソッドのインターフェース（引数や戻り値）が変更されると、それを呼び出しているすべてのAPIエンドポイントを修正する必要があります。また、ビジネスロジックがルーティング層に散在する
         ことになります（ファットコントローラー問題）。

   * `DatabaseManager` とDBスキーマの密結合
       * 問題点: DatabaseManager 内で、SQLクエリが文字列としてハードコードされています。
       * 影響: テーブル名やカラム名といったDBスキーマの変更が、このファイル内の多数のクエリ文字列の修正を必要とします。これは非常にエラーを起こしやすい作業です。
       * 提案: src/database/models.py で定義されているSQLAlchemyのモデルを、DatabaseManager 内でも活用（または完全に移行）し、ORMを介してデータベースを操作することで、スキーマ変更への耐性を高めるべきです。

   * OCR関連モジュールと設定ファイルの密結合
       * 問題点: src/core/ocr/ 以下の多くのモジュールが、config.py からROIのカテゴリリスト (POKEMON_NAME_ROIS など) を直接インポートしています。
       * 影響: ROIのカテゴリ分けという「ロジック」が設定ファイルに記述されており、この分類ルールを変更すると、config.py を利用するすべてのモジュールに意図しない影響が及ぶ可能性があります。

  3. レイヤー違反

  アプリケーションの階層構造が守られておらず、ショートカットするような呼び出しが見られます。

   * サービスレイヤーの欠如
       * 問題点: 前述の通り、ルーティング層 (Routes) とデータアクセス層 (Database) の間に、ビジネスロジックを担うべきサービス層が存在しません。
       * 影響: 本来サービス層が担うべき「複数のデータアクセス処理の組み合わせ」や「ビジネスルールの適用」といったロジックが、ルーティング層やデータアクセス層に漏れ出してしまっています。これにより、各レイヤーの責
         務が曖昧になり、コードの再利用性やテストの容易性が損なわれます。
       * 提案: services ディレクトリを新たに作成し、party_service.py, dashboard_service.py のようなファイルを用意します。例えば dashboard_service.get_dashboard_data() は、内部で DatabaseManager
         の複数のメソッドを呼び出してデータを取得・加工し、その結果を routes/api/dashboard.py に返す、という形に責務を分離します。

  4. グローバル変数の使用

  スレッド間の状態共有にグローバル変数が使われており、これは堅牢性の観点で大きな問題です。

   * `src/state.py`
       * 問題点: video_tasks, capture_thread, ocr_thread, background_thread_stop_event, shared_game_state といった変数がグローバルに定義され、複数のモジュール（sockets/handlers.py, workers/*.py
         など）から直接参照・変更されています。
       * 影響:
           1. 競合状態 (Race Condition): 複数のスレッドが同時に同じ変数を書き換えることで、データが破損したり、予期せぬ状態に陥る可能性があります（game_state_lock
              で一部は保護されていますが、根本的な解決にはなっていません）。
           2. 追跡困難: グローバル変数はどこからでも変更できるため、問題が発生した際に原因を特定するのが非常に困難です。
           3. テスト不能: グローバルな状態に依存するコンポーネントは、独立してテストすることがほぼ不可能です。
       * 提案:
           * 状態管理クラスの導入: アプリケーションの状態を管理する専用のクラス（例: AppState）を作成し、Flaskのアプリケーションコンテキスト (g オブジェクト)
             やDI（依存性注入）コンテナを通じて各コンポーネントに渡すようにします。
           * セッション管理: ui/routes.py の simulations = {} のようなユーザーセッションに紐づくデータは、Flask-Sessionなどの拡張機能を用いて、ファイルやRedisなどの永続的なストレージに保存すべきです。

  5. ハードコードされた設定値

  設定ファイルに分離すべき値が、コード内に直接書き込まれています。

   * 絶対パスの使用
       * 問題点: src/core/ocr/config.py や src/core/ocr/db_access.py など、多くのファイルで C:\pokemon-ai-tool\... のような絶対パスがハードコードされています。
       * 影響: このままでは、開発者の環境やデプロイ先のサーバーがWindowsで、かつ同じディレクトリ構造でない限り、アプリケーションは動作しません。移植性が完全に失われています。
       * 提案: os.path.dirname(__file__) を基準とした相対パスで構築するか、環境変数 (.env ファイルなど) からルートパスを読み込むように変更すべきです。

   * マジックナンバー/マジックストリング
       * 具体例:
           * src/ai/win_rate_predictor.py: 相性計算のスコア (score += 2)
           * src/routes/api/battle.py: 対戦形式 ('シングル')
           * src/workers/capture.py: 保存先のファイルパス ('static/captures/latest_frame.jpg')
       * 影響: これらの値が何を表しているのかがコードから読み取りづらく、将来変更が必要になった際に、複数箇所を修正する必要が出てくる可能性があります。
       * 提案: 定数として名前を付けて、設定ファイルや各モジュールの先頭で定義すべきです。例: BATTLE_FORMAT_SINGLE = 'シングル'。

  総括

  このプロジェクトは、機能分割の点では良いスタートを切っていますが、アーキテクチャのレイヤー化が不十分であり、状態管理に大きな課題を抱えています。特に、サービスレイヤーの導入による責務の分離と、グローバル変数
  を廃した堅牢な状態管理機構の構築が、今後の開発と保守を容易にする上で最も重要な改善点となります。ハードコードされたパスや設定値の外部化も、移植性を確保するために急務です。
