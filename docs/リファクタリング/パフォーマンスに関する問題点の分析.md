 パフォーマンスに関する問題点の分析

  1. N+1 クエリ問題

  ループ内で都度クエリが発行されており、データ量が増えるにつれてパフォーマンスが劇的に悪化する典型的なN+1問題が複数存在します。

   * `src/database/manager.py` の `_get_party_members` メソッド
       * 問題点: このメソッドは、パーティに所属するメンバーのIDリストを取得した後、ループ内でメンバー1体ごとに `get_trained_pokemon_by_id` を呼び出しています。 get_trained_pokemon_by_id
         自体も、技情報を取得するためにさらにループ内でクエリを発行するため、問題が深刻化しています。
       * 影響: 6体のパーティ情報を1つ取得するために、1 (party) + 1 (members) + 6 * (1 (base) + 1 (item) + 4 (moves)) のように、数十のクエリが発行される可能性があります。
       * 提案: trained_pokemon_id のリストを取得した後、WHERE id IN (...) 句を使って、必要なポケモンと技の情報をそれぞれ一括で取得し、Python側でマージするようにクエリを書き換えるべきです。

   * `src/database/manager.py` の `get_all_parties` メソッド
       * 問題点: 全パーティのリストを取得した後、ループ内でパーティごとに `_get_party_members` を呼び出しています。 これにより、上記のN+1問題がパーティの数だけ繰り返されます。
       * 影響: 10個のパーティがあれば、発行されるクエリは数百に達する可能性があり、パーティ一覧ページの表示が極端に遅くなります。
       * 提案: 最初に parties, party_members, trained_pokemons を JOIN したクエリで必要なデータをすべて取得し、Python側でパーティごとにグルーピングする処理に切り替えるべきです。

   * `src/database/manager.py` の `get_selection_pattern_win_rate` メソッド
       * 問題点: 選出パターンをPythonで組み立てた後、ループ内でパターンごとに勝敗結果を取得するクエリ (`SELECT result FROM battles WHERE battle_id = ?`) を発行しています。
       * 影響: 対戦ログが増えるほど、このループで発行されるクエリ数が増加します。
       * 提案: 最初に parties_log と battles を JOIN して必要な情報をすべて取得し、Pythonのループ内ではDBにアクセスしないように修正すべきです。

  2. 非効率なデータ集計とインデックスの欠如

  データベースの機能を十分に活用せず、アプリケーション側で重い集計処理を行っている箇所や、インデックス不足によるパフォーマンス低下が懸念される箇所があります。

   * `src/database/manager.py` の `get_win_rate_by_opponent` メソッド
       * 問題点: 「相手のポケモンごとの勝率」という集計処理を、parties_log と battles から全データを取得してからPythonの辞書を使って手動で計算しています。
       * 影響: 対戦ログが数千、数万件と増えた場合、大量のデータをメモリにロードすることになり、メモリ使用量と処理時間の両方でパフォーマンスが著しく低下します。
       * 提案: この処理はSQLの JOIN, GROUP BY, AVG を使ってデータベース側で効率的に実行できます。クエリを以下のように見直すべきです。

   1         SELECT
   2             pl.pokemon_name,
   3             COUNT(b.battle_id) as total_matches,
   4             AVG(CASE WHEN b.result = 'win' THEN 1.0 ELSE 0.0 END) * 100 as win_rate
   5         FROM parties_log pl
   6         JOIN battles b ON pl.battle_id = b.battle_id
   7         WHERE pl.is_opponent = 1
   8         GROUP BY pl.pokemon_name;

   * インデックスの欠如
       * 問題点: スキーマ定義ファイルがないため断定はできませんが、クエリから判断するに、多くの検索・結合キーにインデックスが設定されていない可能性が高いです。
       * 影響: データ量が増加すると、テーブルのフルスキャンが多発し、JOINやWHERE句のパフォーマンスが大幅に低下します。
       * 提案: 少なくとも以下のカラムにはインデックスを作成すべきです。
           * 外部キー: trained_pokemons(pokemon_id), party_members(party_id, trained_pokemon_id), parties_log(battle_id, pokemon_id) など。
           * 頻繁な検索条件: pokemons(name_ja), battles(battle_id), parties_log(is_opponent, pokemon_name)。
           * ソートキー: parties(updated_at), trained_pokemons(updated_at)。

  3. 同期的な重い処理（OCR、動画解析）

   * `src/routes/api/video.py` の `upload_video` エンドポイント
       * 評価: executor.submit(analyze_video_task, ...)
         を使い、重い動画解析処理をバックグラウンドのスレッドにオフロードしている点は非常に良い設計です。これにより、APIリクエストが長時間ブロックされるのを防いでいます。
       * 潜在的な問題点: デフォルトの ThreadPoolExecutor は、PythonのGIL（Global Interpreter Lock）の制約により、CPUバウンドな処理（画像処理やOCRなど）をマルチコアで並列実行できません。
       * 影響: 複数の動画解析リクエストが同時に発生した場合、CPUが律速となり、全体の処理スループットが上がらない可能性があります。
       * 提案: flask_executor の設定を変更し、ProcessPoolExecutor を使用することを検討します。これにより、複数のプロセスで処理が実行され、マルチコアCPUの性能を最大限に活用できます。

  4. メモリリークの可能性

  アプリケーションの実行時間が長くなるにつれて、メモリ使用量が増え続ける可能性のある箇所が存在します。

   * `src/routes/api/video.py` の `state.video_tasks`
       * 問題点: upload_video が呼び出されるたびに、グローバル変数である state.video_tasks 辞書にタスクIDとステータスが追加されます。しかし、完了したタスクをこの辞書から削除する仕組みが存在しません。
       * 影響: アプリケーションを再起動しない限り、video_tasks 辞書は増大し続けます。これは典型的なメモリリークであり、長期間の運用でメモリを枯渇させる原因となります。
       * 提案:
           1. タスクのステータスを取得する際に、完了（DONE or ERROR）してから一定時間（例: 10分）が経過したタスクを辞書から削除するクリーンアップ処理を追加します。
           2. より堅牢な解決策として、タスクの状態管理をRedisやデータベースなどの永続的なストレージに移行することを検討します。

   * `src/database/manager.py` のデータ集計メソッド
       * 問題点: get_win_rate_by_opponent など、Python側で集計を行うメソッドは、処理中にDBから取得した全データをメモリ上に展開します。
       * 影響: これは厳密なメモリリークではありませんが、対戦ログが巨大になると、リクエストごとに大量のメモリを一時的に消費し、サーバー全体のパフォーマンスを低下させる可能性があります。
       * 提案: 前述の通り、これらの集計処理は可能な限りSQLで実行し、アプリケーション側で保持するデータ量を最小限に抑えるべきです。
