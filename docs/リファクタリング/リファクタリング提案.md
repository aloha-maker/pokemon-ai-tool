リファクタリング提案

  1. 長すぎる関数（100行超）

   * `src/database/manager.py` の `save_battle_result_with_log` 関数 (約110行)
       * 問題点: この関数は、対戦結果とOCRログを保存するという単一の責任を持ちながら、内部でマスタデータ取得、既存ログ削除、自パーティ処理、相手パーティ処理、先発ポケモン記録、RAWイベント記録など、多数の処理を直
         列に実行しており、非常に長大で複雑になっています。
       * 提案:
           1. パーティのログを処理する内部関数 _process_party_log
              は、さらに「ポケモンの詳細情報を整形する」「pokemons_logに保存する」「parties_log用のタプルを生成する」といった小さなプライベートメソッドに分割できます。
           2. マスタデータの事前取得、既存ログの削除、各パーティの処理、先発記録、イベント記録を、それぞれ独立したプライベートメソッドとして切り出すことを検討します。

   * `src/ai/party_generator.py` の `generate` 関数 (約100行)
       * 問題点: パーティ生成のコアロジックであり、データ取得、役割付与、候補フィルタリング、タイプバランスを考慮した選出、詳細設定、運用ガイド生成といった多くのステップを含んでいます。
       * 提案:
           1. 「パーティ6体を選出するロジック」と「選出された6体に詳細（技、持ち物など）を設定するロジック」を別のメソッドに分離します。
           2. タイプバランスを考慮して最適な候補を見つけるループ (while len(party) < 6:) は、それ自体が複雑なため _select_balanced_pokemon のようなメソッドとして独立させることができます。

   * `src/database/manager.py` の `get_selection_pattern_win_rate` 関数 (約60行)
       * 問題点: 100行には達していませんが、Pythonコードで複雑なデータ集計を行っており、SQLで実行できる可能性のある処理をアプリケーション層で行っているため、パフォーマンスと可読性の両面で問題があります。
       * 提案: この集計ロジックは、可能であればSQLのWindow関数や共通テーブル式(CTE)を用いてデータベース内で完結させることを検討します。SQLiteで複雑なクエリが難しい場合でも、データ取得部分とPythonでの集計部分をよ
         り明確に分離すべきです。

  2. 複雑度が高い箇所

   * `src/database/manager.py` の `save_battle_result_with_log` と `get_win_rate_by_opponent`
       * 問題点: 前者は上述の通り長大で、後者はDBから取得した複数のリストをPythonのループで処理しており、計算量がデータ量に比例して増加します (O(N*M)に近い)。
       * 提案: get_win_rate_by_opponent は、battlesテーブルとparties_logテーブルをJOINし、GROUP BY pokemon_name と AVG(CASE WHEN result = 'win' THEN 1 ELSE 0 END)
         を使うことで、SQL一発で効率的に計算できる可能性があります。

   * `src/ai/party_generator.py` の `generate` 関数
       * 問題点: タイプ相性を考慮してパーティを選ぶロジックは、弱点を計算し、全候補とのスコアを比較するため、ネストが深くなりがちです。
       * 提案: スコアリングロジックを _calculate_compatibility_score(pokemon, current_party) のような形で独立した関数に切り出し、可読性を向上させます。

  3. 重複コード

   * `src/database/manager.py` のJSONパース処理
       * 問題点: get_battle_history, get_battle_log_by_id, get_all_battle_logs の各関数内で、battle_data や opponent_party を json.loads する try-except ブロックが繰り返し現れます。
       * 提案: _parse_log_json(log_data) のようなプライベートヘルパーメソッドを作成し、JSONのパース処理を共通化します。

   * `src/database/manager.py` の `get_abilities_by_pokemon_id` と `get_moves_by_pokemon_id`
       * 問題点: どちらも「カンマ区切りのID文字列をパースし、対応するマスタテーブルから情報を取得する」という全く同じロジックです。
       * 提案: _get_details_from_comma_separated_ids(self, pokemon_id, master_table, column_name) のような汎用的なプライベートメソッドに統合できます。

   * `src/core/ocr/ocr_processor.py` のフェーズ別処理
       * 問題点: _process_select_rois, _process_battle_choose_rois, _process_battle_act_rois は、ROIのリストをループしてそれぞれのプロセッサーを呼び出すという類似した構造を持っています。
       * 提案: ROIの種類（OCR, Image, Special）に応じて処理を振り分ける汎用的な _process_rois(self, frame, roi_list, ...) メソッドを作成し、各フェーズの関数からはそのメソッドを呼び出すだけにします。

  4. エラーハンドリングの不備

   * API全体にわたる `except Exception as e:`
       * 問題点: src/routes/api/ 以下のほぼすべてのエンドポイントで、except Exception as e: return jsonify({"error": str(e)}), 500
         という包括的なエラーハンドリングが使われています。これにより、予期せぬ内部エラー（DB接続エラー、設定ファイル欠損など）の詳細が str(e) を通じて外部に漏洩する可能性があります。
       * 提案:
           1. Flaskの app.errorhandler(Exception) を使って、予期せぬ例外をグローバルに捕捉するハンドラを設けます。
           2. そのハンドラ内で、エラーの詳細をファイルや監視サービスにログとして記録し、クライアントには「Internal Server Error」のような汎用的なメッセージのみを返すようにします。
           3. traceback.print_exc() はデバッグ時には有用ですが、本番環境のコードからは削除し、ロギング機構に置き換えるべきです（例: loggingモジュール）。

         のような相対パスを指定することで、意図しないファイルにアクセスされる危険性があります。
       * 提案: image_path が、想定されるディレクトリ（例: static/captures）内に存在することを必ず検証します。os.path.abspath
         で絶対パスに変換し、それが特定のディレクトリで始まっているかを確認する処理を追加します。

  総括

  このアプリケーションは、機能ごとにモジュールが分割されており、良好な基本設計がなされています。しかし、特に DatabaseManager
  にロジックが集中し、一部の関数が肥大化・複雑化しています。また、APIのエラーハンドリングとテストの欠如が、品質と保守性における最大のリスク要因です。

  リファクタリングに着手する際は、まずテストハーネス（テスト環境）を整備し、主要な機能に対するテストを記述することを最優先事項として推奨します。安全なテストのカバレッジを確保した上で、本ドキュメントで指摘した
  関数の分割や重複コードの共通化を進めていくのが安全かつ効率的なアプローチです。
