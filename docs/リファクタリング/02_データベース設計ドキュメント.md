 データベース設計ドキュメント

  1. 概要

  このドキュメントは「ポケモン対戦補助AIツール」のデータベース設計について記述します。アプリケーションで扱われる主要なデータモデル、物理的なテーブル構造、テーブル間の関係、そして主要なデータアクセスパターンを
  定義します。

  2. データモデル (概念モデル)

  アプリケーションは以下の主要な概念モデルに基づいています。

   * マスターデータ:
       * ポケモン (`Pokemon`): ポケモン図鑑に相当する静的な情報。種族値、タイプ、覚える技など。
       * 技 (`Move`): 技の効果、タイプ、威力などの静的な情報。
       * 特性 (`Ability`), 性格 (`Nature`), 持ち物 (`Item`), タイプ (`Type`): それぞれの静的なマスター情報。

   * ユーザーデータ:
       * 育成済みポケモン (`TrainedPokemon`): ユーザーが育成した個々のポケモン。ニックネーム、レベル、努力値、覚えさせた技、持ち物など、具体的なカスタマイズ情報を持つ。
       * パーティ (`Party`): ユーザーが作成した「育成済みポケモン」の集合（最大6体）。パーティ名と説明を持つ。

   * ログデータ:
       * 対戦 (`Battle`): 一回の対戦そのものを記録する。勝敗結果、対戦フォーマット、対戦日時など。
       * 対戦パーティログ (`PartyLog`): ある対戦で、自分と相手がどのポケモンをパーティに入れ、そのうちどれを選出したかを記録する。
       * 対戦ポケモンログ (`PokemonLog`): ある対戦で観測されたポケモンの具体的な情報を記録する。相手のポケモンの持ち物やテラスタイプなど、対戦中に判明した情報を格納する。
       * RAWイベント (`RawBattleEvent`): リアルタイムOCRで読み取った情報の生ログ。「どの領域」から「何が」読み取れたかを時系列で記録する。

  3. データベーススキーマ (物理モデル)

  manager.py内のクエリから、以下のテーブル構造が推定されます。

  マスターデータテーブル群

   * pokemons (ポケモンマスタ)

  ┌─────────────────┬─────────┬─────────────────────────────────┐
  │ 列名            │ 型      │ 説明                            │
  ├─────────────────┼─────────┼─────────────────────────────────┤
  │ id              │ INTEGER │ 主キー                          │
  │ name            │ TEXT    │ 英語名                          │
  │ name_ja         │ TEXT    │ 日本語名                        │
  │ type1, type2    │ TEXT    │ タイプ                          │
  │ hp, attack, ... │ INTEGER │ 種族値                          │
  │ abilities       │ TEXT    │ 習得可能な特性ID (カンマ区切り) │
  │ moves           │ TEXT    │ 習得可能な技ID (カンマ区切り)   │
  └─────────────────┴─────────┴─────────────────────────────────┘

   * moves, abilities, items, natures, types
       * これらは共通して id, name, name_ja といったカラムを持つシンプルなマスターテーブルです。

  ユーザーデータテーブル群

   * trained_pokemons (育成済みポケモン)

  ┌───────────────────────┬─────────┬──────────────────────────┐

  ├───────────────────────┼─────────┼──────────────────────────┤
  │ id                    │ INTEGER │ 主キー                   │
  │ pokemon_id            │ INTEGER │ pokemons.idへの外部キー  │
  │ nickname              │ TEXT    │ ニックネーム             │

  │ tera_type_id            │ INTEGER │ types.idへの外部キー     │

  │ nature_id             │ INTEGER │ natures.idへの外部キー   │

  │ move1_id, move2_id, ... │ INTEGER │ moves.idへの外部キー     │

  5. 主要なクエリパターン

  DatabaseManagerクラスは、以下のようなクエリパターンを実装しています。

   * CRUD操作:
       * get_all_trained_pokemons, add_trained_pokemon, update_trained_pokemon, delete_trained_pokemon
       * get_all_parties, add_party, update_party, delete_party
       * これらは、ユーザーが育成したポケモンや作成したパーティを管理するための基本的なクエリです。

   * JOINによる詳細情報取得:
       * get_trained_pokemon_by_id: trained_pokemonsテーブルを起点に、pokemons, items, movesなど複数のマスターテーブルをLEFT JOINし、一匹のポケモンの完全な情報を取得します。
       * _get_party_members: party_membersを経由して、パーティに所属する複数の育成済みポケモンの詳細をまとめて取得します。

   * 対戦ログの保存:
       * save_battle_result_with_log: 最も複雑なクエリの一つ。一回の対戦結果を受け取り、battles, pokemons_log, parties_log,
         raw_battle_eventsの各テーブルに正規化されたデータをトランザクション内で書き込みます。冪等性を担保するために、既存ログの削除処理も含まれます。

   * 集計・分析クエリ (ダッシュボード用):
       * get_opponent_pokemon_ranking: parties_logテーブルをGROUP BYし、相手の使用ポケモンランキングを集計します。
       * get_win_rate_by_opponent: parties_logとbattlesを組み合わせ、相手のポケモンごとの勝率を算出します。
       * get_my_pokemon_selection_rate: parties_logテーブルから自分のポケモンの選出率を計算します。
       * get_selection_pattern_win_rate: 3体の選出パターンの組み合わせごとに勝率を集計します。

  これらのクエリパターンは、アプリケーションの各機能（パーティ管理、対戦分析、ダッシュボード表示など）と密接に対応しています。
