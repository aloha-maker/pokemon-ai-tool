 総合リファクタリング計画：優先度順リスト

  【P0】最優先：セキュリティおよび環境分離の問題

  これらの項目は、アプリケーションを安全に運用し、他環境へ展開するための最低条件です。

   * 優先度: P0
   * リスクレベル: Critical
   * 影響範囲: app.py, src/core/ocr/config.py, src/database/manager.py, src/routes/api/*.py, requirements.txt
   * 改善工数の見積もり: 中
   * 推奨する対応順序:
       1. 依存関係の固定: pip freeze > requirements.txt を実行し、全ライブラリのバージョンを == で固定する。これにより、意図しないライブラリの更新による破壊的変更を防ぎます。
       2. 設定管理の標準化: Flask標準の構成管理方法を導入します。
           * プロジェクトルートに config.py を作成し、DevelopmentConfig, ProductionConfig などを定義します。
           * app.py の create_app 内で、環境変数 FLASK_ENV を見て設定を読み込むように変更します。
           * debug=True などのハードコードされた値を config.py に移管します。
       3. 秘匿情報と絶対パスの排除:
           * python-dotenv を導入し、.env ファイルで SECRET_KEY やデータベースのパス、Tesseractのパスなどを管理します。
           * コード内のすべてのハードコードされた絶対パスを、app.config から読み込むように修正します。
       4. 情報漏洩の防止: 全てのAPIエンドポイントのエラーレスポンスから str(e) を削除し、汎用的なメッセージに置き換えます。同時に、Pythonの logging
          モジュールを導入し、例外のスタックトレースをサーバー側のファイルに記録するようにします。
       5. 脆弱性の修正: src/routes/api/capture.py のパス・トラバーサルの脆弱性を修正します。
   * 依存関係: 他のすべてのリファクタリングの基礎となります。特にテスト環境の構築にも影響します。

  ---

  【P1】高優先度：安定稼働とパフォーマンスの基盤構築

  P0が完了次第、アプリケーションの品質を担保し、スケールさせるための基盤を構築します。

   * 優先度: P1
   * リスクレベル: High
   * 影響範囲: tests/ (新規作成), src/database/manager.py, src/state.py, src/routes/api/video.py
   * 改善工数の見積もり: 大
   * 推奨する対応順序:
       1. テストフレームワークの導入 (最優先): pytest を導入し、まずは DatabaseManager の主要なメソッドに対する単体テストを作成します。これがなければ、以下のDBリファクタリングは安全に行えません。
       2. N+1クエリの解消: テストで安全性を確保した上で、_get_party_members と get_all_parties のN+1クエリを JOIN を使った効率的なクエリに修正します。パフォーマンスへの影響が最も大きい問題です。
       3. DBインデックスの追加: parties_log(battle_id) や trained_pokemons(pokemon_id) など、JOINやWHERE句で頻繁に使われるカラムにインデックスを追加します。
       4. メモリリークの修正: src/routes/api/video.py で利用されている state.video_tasks について、完了したタスクを定期的に削除する機構を導入します。
   * 依存関係: P0の完了が望ましいです。 特にテストの作成は、これ以降のすべてのリファクタリングの前提条件となります。

  ---

  【P2】中優先度：アーキテクチャの改善

  アプリケーションの保守性と拡張性を長期的に高めるための、より大きな構造的リファクタリングです。

   * 優先度: P2
   * リスクレベル: Medium
   * 影響範囲: src/ 全体 (特に routes/api/, database/manager.py, ai/)
   * 改善工数の見積もり: 大
   * 推奨する対応順序:
       1. サービスレイヤーの導入: src/services ディレクトリを作成し、APIエンドポイントと DatabaseManager の間にサービス層を設けます。get_dashboard_data
          のようなビジネスロジックをルーティング層からサービス層に移管します。
       2. `DatabaseManager` の責務分離: サービス層の導入に伴い、DatabaseManager から分析系の複雑なクエリ（get_win_rate_by_opponentなど）を対応するサービスクラスに移管し、DatabaseManager
          を純粋なデータアクセス層に近づけます。
       3. レスポンス形式の統一: APIの成功時レスポンスを {"status": "success", "data": ...} のような標準エンベロープ形式に統一します。
       4. 状態管理の改善: src/state.py のグローバル変数を廃止し、状態を管理する専用のクラスを設計・導入します。
   * 依存関係: P1のテスト導入が完了していることが絶対条件です。 アーキテクチャレベルの変更は影響範囲が広いため、十分なテストカバレッジなしに行うべきではありません。

  ---

  【P3】低優先度：コード品質の向上

  機能やパフォーマンスに直接的な影響は少ないものの、将来の開発効率を高めるためのコードレベルのクリーンアップです。

   * 優先度: P3
   * リスクレベル: Low
   * 影響範囲: src/ai/party_generator.py, src/database/manager.py など
   * 改善工数の見積もり: 小〜中
   * 推奨する対応順序:
       1. 長大関数の分割: save_battle_result_with_log や party_generator.generate を、より小さなプライベートメソッドに分割します。
       2. 重複コードの共通化: DatabaseManager 内のJSONパース処理や、カンマ区切りIDの処理などをヘルパーメソッドに共通化します。
       3. 不要なライブラリの削除: requirements.txt から fastapi などを削除します。
   * 依存関係: P1, P2が完了し、テストが整備された後であれば、いつでも安全に着手できます。

  この順序で改善を進めることで、リスクを最小限に抑えながら、アプリケーションをより堅牢で保守性の高いものへと進化させることができます。
