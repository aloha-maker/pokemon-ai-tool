# 最低限の開発標準 v0.1

## 1. このドキュメントの目的と適用範囲

### 1.1. 目的
このドキュメントは、「ポケモン対戦補助AIツール」開発プロジェクトにおけるバックエンド（Python/Flask）の品質、セキュリティ、保守性を担保するための最低限のルールを定義します。
技術的負債の蓄積を防ぎ、チームメンバー全員が共通認識を持って効率的に開発を進めることを目的とします。

### 1.2. 適用範囲
この標準は、本日以降に**新規で作成される、または修正が加えられるすべてのバックエンド関連コード**に適用されます。
既存コードがこの標準を満たしていない場合でも、修正箇所およびその周辺コードは、可能な限りこの標準に準拠させる必要があります。

---

## 2. 【P0】即座に対応必須のセキュリティ要件

これらの要件は、アプリケーションの基本的な安全性を確保するために、いかなる場合でも遵守されなければなりません。

| ID | 要件 | 理由 |
| :--- | :--- | :--- |
| SEC-01 | **秘匿情報（Secret）をコードに含めない** | `SECRET_KEY`、外部APIキー、パスワードなどの秘匿情報は、コード内に直接記述してはならない。必ず環境変数または `.env` ファイルから読み込むこと。 |
| SEC-02 | **エラー詳細をクライアントに返さない** | APIのエラーレスポンスに、例外のスタックトレースや生のメッセージ (`str(e)`) を含めてはならない。サーバー側でのみログに記録し、クライアントには汎用的なメッセージを返すこと。 |
| SEC-03 | **ファイルパスの検証** | ユーザー入力やリクエストパラメータに由来するファイルパスは、必ず想定されたディレクトリ内に存在するかを検証し、ディレクトリトラバーサルの脆弱性を防ぐこと。 |

---

## 3. 【P0】環境管理の必須要件

開発効率と本番環境での安定稼働を両立させるための必須要件です。

| ID | 要件 | 理由 |
| :--- | :--- | :--- |
| ENV-01 | **依存関係のバージョンを固定する** | `requirements.txt` に記載するすべてのライブラリは、`==` を用いてバージョンを完全に固定すること。これにより、環境ごとの差異や意図しないアップデートによる破壊的変更を防ぐ。 |
| ENV-02 | **絶対パスをコードに含めない** | `C:\...` のようなハードコードされた絶対パスは禁止する。パスは設定ファイルから読み込むか、プロジェクトルートからの相対パスで動的に構築すること。 |
| ENV-03 | **設定による環境分離** | `config.py` と環境変数 `FLASK_ENV` を用い、開発(Development)と本番(Production)の設定を明確に分離すること。`debug=True` のような危険な設定をハードコードしてはならない。 |

---

## 4. 禁止事項リスト

以下のパターンは、コードの品質と保守性を著しく低下させるため、**原則として禁止**します。

- **安易なコンソール出力**: デバッグ目的以外の `print()` や `traceback.print_exc()` の使用。サーバーログは必ず `logging` モジュール経由で出力する。
- **ロジックの不適切な配置**: 新しいビジネスロジックをルーティング層 (`routes/api/`) や `DatabaseManager` に直接実装すること。必ずサービス層 (`services/`) に実装する。
- **グローバル状態の追加**: `src/state.py` のようなグローバル変数を用いた状態管理の追加。状態はアプリケーションコンテキストや専用のクラスで管理する。
- **テストのないマージ**: 新機能・バグ修正・リファクタリングにおいて、対応するテストコードがないまま `main` ブランチにマージすること。
- **一貫性のないレスポンス形式**: APIエンドポイントで、他のエンドポイントと異なる構造の成功/失敗レスポンスを返すこと。

---

## 5. 必須事項リスト

コード品質を一定以上に保つため、以下の項目を**必ず遵守**してください。

- **テストの作成**: すべての新規機能、バグ修正には `pytest` を用いた単体テストまたは結合テストを付随させること。
- **ロギング**: `try-except` で例外を捕捉する際は、必ず `logging.exception()` などを用いてエラーの詳細をログファイルに記録すること。
- **サービスレイヤーの利用**: ビジネスロジックは `src/services/` ディレクトリ配下の適切なサービスクラスに実装し、APIエンドポイントはサービスを呼び出すことに専念する。
- **リクエストの検証**: APIエンドポイントは、受け取ったリクエストデータが期待する形式・型であるかを、Pydanticなどのスキーマ定義を用いて検証すること。
- **N+1クエリの防止**: ループ内でのDBクエリ発行を避け、`JOIN` や `WHERE IN (...)` を用いて一括でデータを取得する。

## 6. コードレビューチェックリスト

Pull Requestをレビューする際は、以下の項目を最低限確認してください。

- [ ] **禁止事項**に違反していないか？
- [ ] **必須事項**（特にテストとロギング）が満たされているか？
- [ ] 新規・変更部分に対する**テストコード**は追加されているか？
- [ ] 設定値（パス、URL、パラメータ）がハードコードされておらず、**設定ファイルや環境変数から**読み込まれているか？
- [ ] 例外処理が適切に行われ、**エラー詳細がクライアントに漏洩しない**ようになっているか？
- [ ] データベースアクセスにおいて、**N+1問題**を引き起こすような非効率なクエリがないか？
- [ ] ロジックが適切なレイヤー（`routes`, `services`, `database`）に配置されているか？

## 7. 例外規定と改善計画

### 7.1. 例外規定
本標準は `v0.1` であり、既存のコードベースの多くが標準を満たしていないことを認識している。したがって、この標準は**新規および修正コードに厳格に適用**される。

やむを得ない事情（緊急のホットフィックスなど）で一時的に標準を遵守できない場合は、テックリードの承認を得た上で、**技術的負債を返済するためのチケットを必ず起票**すること。

### 7.2. 改善計画
既存コードベースをこの標準に準拠させるため、別途作成された「総合リファクタリング計画」に基づき、以下の優先度で改善を進めていく。

1.  **P0**: セキュリティと環境管理の問題を修正。
2.  **P1**: テスト基盤を構築し、主要なパフォーマンス問題と安定性のリスクを解消。
3.  **P2**: サービスレイヤー導入などのアーキテクチャ改善。
4.  **P3**: コードレベルの品質向上（重複排除、長大関数の分割など）。
